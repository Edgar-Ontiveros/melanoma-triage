# F6 — Exportación y API

Especificación para Claude Code. Guardar como `docs/specs/F6.md`.

**Duración estimada:** 1 semana. Todo local, CPU.
**Depende de:** F3 (checkpoint), F4 (calibración y umbrales congelados), F5 (contrato de CAM).
**Bloquea:** F7 (interfaz) y F8 (despliegue).

---

## Objetivo

Que el modelo se pueda servir **sin PyTorch**, con exactamente los mismos números que se
validaron en F4, y con el mapa de calor de F5 calculado en numpy. La API es la pieza que un
usuario final toca, y por eso hereda todos los guardarraíles: nada escrito a mano, todo
verificado contra el modelo original.

**Principio:** la API no conoce ningún número del modelo. Todo lo lee de un paquete
exportado y versionado. Si alguien cambia el umbral a mano en el código, una prueba falla.

## F6.1 — El paquete de modelo

`scripts/export_bundle.py` produce `models/bundle/` (fuera de git; se publica como *release
asset* de GitHub con su SHA256):

| Archivo | Contenido | Origen |
|---|---|---|
| `model.onnx` | Backbone + cabeza, **dos salidas**: `logit [N, 1]` y `features [N, 1280, 7, 7]` | Exportación del checkpoint en `eval()` |
| `preprocess.json` | `input_size`, `interpolation`, `crop_pct`, `mean`, `std`, `val_resize` | **`timm.data.resolve_data_config`**, nunca escrito a mano |
| `calibration.json` | Platt `a`, `b`; método; ajustado sobre validación | Copia de `reports/f4_calibration.json` |
| `thresholds.json` | τ₉₅, τ₉₀, con su especificidad en validación | Idem |
| `cam_weights.npy` | Los 1280 pesos de la capa lineal | Del checkpoint |
| `metrics.json` | AUC-ROC, AUPRC, sens/spec en τ₉₅ **del test**, con IC | Copia de `reports/f4_test_results.json` |
| `manifest.json` | SHA256 de cada archivo, SHA del checkpoint, git SHA, fecha, opset, versiones de torch/onnx/onnxruntime | Generado |

**Reglas de exportación:**
- `model.eval()` antes de exportar: dropout apagado, BatchNorm con estadísticas fijas.
- Opset **17**, fijado en config. Dimensión de lote dinámica.
- Verificar el modelo con `onnx.checker` y con una pasada en `onnxruntime` antes de guardar.
- El SHA256 del checkpoint de entrada se compara contra `reports/f3_final_model.json`. Si no
  coincide, el script se detiene.

**Versión del modelo** = `{git_sha_corto}-{checkpoint_sha_8}`. Aparece en cada respuesta.

## F6.2 — Paridad con PyTorch

`scripts/verify_bundle.py`, sobre **200 imágenes de validación** al azar con semilla:

| Comparación | Criterio |
|---|---|
| Logit ONNX vs PyTorch | `max |Δ|` < 1e-4 |
| Probabilidad Platt (numpy) vs `melanoma.eval.Platt` | `max |Δ|` < 1e-6 |
| CAM desde `features` ONNX × `cam_weights.npy` vs `melanoma.explain.cam_from_features` sobre features de torch | Correlación > 0.999 |
| Decisión en τ₉₅ | **Idéntica** en las 200 |

Además, la **cadena completa** de la API (bytes JPEG → PIL → preprocesamiento numpy →
ONNX → Platt → decisión) contra la cadena de entrenamiento (`build_transforms` con
albumentations → torch): `max |Δ logit|` < 1e-3. La tolerancia es mayor porque el
redimensionado de PIL y el de albumentations no son bit a bit idénticos; F1 ya documentó que
Pillow cambia entre versiones.

Resultados a `reports/f6_parity.json`. Esta verificación corre localmente con imágenes
reales; en CI corre una versión con imágenes sintéticas y un paquete de prueba (ver F6.6).

## F6.3 — La API

Paquete `api/`, separado de `src/melanoma/`. Dependencias en el grupo `api` de `uv`:
`fastapi`, `uvicorn`, `onnxruntime`, `numpy`, `pillow`, `pydantic`. **Nada más.**
`test_api_dependency_isolation` (F0) sigue vigente.

### Endpoints

**`POST /predict`** — multipart con un archivo de imagen.

Respuesta:
```json
{
  "model_version": "6c330a8-e0ecf981",
  "probability": 0.034,
  "refer": true,
  "threshold": 0.0039,
  "operating_point": {
    "sensitivity_target": 0.95,
    "sensitivity_test": 0.965,
    "specificity_test": 0.428
  },
  "cam": {
    "status": "ok",
    "grid": [[0.0, 0.12, ...], ...],
    "png_base64": "..."
  },
  "input": {"width": 1024, "height": 768, "format": "JPEG"},
  "latency_ms": 91,
  "disclaimer": "..."
}
```

- `probability` es la **calibrada** (Platt). Nunca se devuelve la cruda.
- `refer` = `probability >= threshold` con τ₉₅. Es un booleano de triage, no un diagnóstico.
- `cam.status`: `"ok"` o `"no_positive_evidence"` (las 181 de F5: mapa todo cero → `grid`
  de ceros y `png_base64: null`). Nunca se normaliza un mapa nulo para que "se vea algo".
- `cam.png_base64`: el mapa 7×7 interpolado a 224 y superpuesto sobre el recorte que vio el
  modelo, como PNG. El recorte, no la imagen original: así se ve exactamente lo que el modelo
  evaluó.
- `disclaimer`: texto fijo, en español, que diga que es una herramienta de apoyo al triage
  de melanoma, que no detecta otros cánceres de piel, que no sustituye la valoración de un
  dermatólogo, y que no tiene aprobación regulatoria. **Va en cada respuesta**, no solo en la
  documentación.

**`GET /health`** — `{"status": "ok", "model_version": "..."}`. Falla si el paquete no cargó.

**`GET /model-info`** — el `manifest.json` más `metrics.json` y `thresholds.json`. La API
se describe a sí misma con las métricas validadas y sus intervalos. Un usuario puede saber
qué desempeño tiene lo que está usando sin buscar la tesis.

### Preprocesamiento

`api/preprocess.py` lee `preprocess.json` y reproduce la transformación de validación con
PIL + numpy: lado corto a 224 con la interpolación declarada → CenterCrop 224 → `/255` →
`(x − mean) / std` → `CHW` → `float32`. **Ninguna constante en el código.** Una prueba
verifica que si `preprocess.json` cambia `mean`, la salida cambia.

### Validación de entrada

- Tipos aceptados: JPEG, PNG, WebP. Cualquier otro → 415.
- Tamaño máximo: 10 MB → 413.
- Lado mínimo: 64 px → 422 (una imagen de 32 px no es una dermatoscopía).
- Archivo que PIL no puede abrir → 422 con mensaje claro.
- Un solo archivo por petición; sin lotes en esta fase.

### Carga del paquete

Al arrancar, la API lee `MODEL_BUNDLE_DIR`, verifica **todos los SHA256 del manifiesto**
contra los archivos, y se niega a levantar si alguno no coincide. Un paquete a medias no
sirve predicciones.

## Qué esperar

La paridad debería salir limpia a la primera si `eval()` se llamó antes de exportar; si el
logit difiere en más de 1e-3, casi siempre es dropout o BatchNorm en modo de entrenamiento.

La latencia probablemente quede entre 60 y 150 ms p50 en la laptop.

La imagen Docker debería quedar entre 250 y 320 MB: `onnxruntime` es la dependencia grande.

Y algo que vas a notar: la API va a devolver `refer: true` para la mayoría de las imágenes
benignas que le mandes, porque τ₉₅ está calibrado para sensibilidad 0.95 y la especificidad
es 0.43. No es un bug. Es el punto de operación de F4, y F7 tiene que mostrarlo de forma que
se entienda: probabilidad y contexto, no un semáforo.

### Ajuste antes de F7 (2026-09-21): dos etapas de preprocesamiento y paridad con originales

Pedido de Edgar: la paridad se había medido con las imágenes de 512 px, pero los usuarios
suben originales de hasta 6,000 px, y las de entrenamiento pasaron por dos etapas (PIL a 512
de lado largo en F1, luego cúbico a 224). Commit `4e7ab61`.

1. **Dos etapas en la API.** `preprocess.json` incluye ahora `stage1` (lado largo 512,
   Lanczos, JPEG 95, `draft`), leído de `configs/data/isic2020.yaml` (`data.resize`) en la
   exportación. `services/api/preprocess.py` replica `resize_one` de F1 en memoria (incluida
   la reencodificación JPEG, porque el modelo vio píxeles recomprimidos) y no hace nada si el
   lado largo ya es ≤ 512; después el cúbico a 224 + recorte central de siempre.
   `test_stage1_matches_f1_resize` comprueba la réplica bit a bit contra `resize_one`.
2. **Paridad con originales.** `verify_bundle` tiene una sexta comparación: 100 originales de
   `data/raw/isic2020/train` de validación (lado largo 640–6,000 px) por la cadena de la API
   contra `resize_one` de F1 a disco + cadena de entrenamiento. Resultado: máx |Δ logit|
   **9.3e-6**, media 2.4e-6, decisiones idénticas. La prueba a 512 px pasó a **1.7e-5** (era
   6.5e-3). `all_pass = true`; el criterio 2 se cumple sin desviaciones.
3. **OpenCV en el grupo `api`.** Decisión: sí. `cv2.resize(INTER_CUBIC)` es la misma función
   que usó albumentations, la paridad es exacta y desaparece el cúbico en numpy (≈ 40 líneas de
   código numérico propio). Costo: la imagen pasa de 92.0 a **152.1 MB** (límite 400).
   La etapa 2 bajó de ≈ 20 ms a ≈ 3 ms por petición.
4. **Reexportación.** Paquete `4e7ab61-e0ecf981` (80.6 MB; el ONNX y los pesos no cambian,
   solo `preprocess.json` y el manifiesto). Latencia: p50 35.2 / p95 45.2 / p99 52.0 ms con la
   imagen de 512 px; p50 50.1 / p95 60.0 / p99 64.6 ms con el original de 1872 × 1053 px
   (`reports/f6_latency_original.md`). Con la misma lesión, el original y la versión de 512 px
   dan la misma probabilidad (0.015491). Release republicado: `model-4e7ab61-e0ecf981`,
   `melanoma-bundle-4e7ab61-e0ecf981.tar.gz`, SHA256
   `a884adac90fa6924ee090702d728606c30ecbfadf3b9efab4583064dbd38465d`; el release
   `model-6c330a8-e0ecf981` se retiró.
