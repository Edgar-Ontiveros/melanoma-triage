---

## Objetivo

Dejar un repositorio real, reproducible y verificable, con integración continua en verde y
una prueba de humo de entrenamiento que corre en CPU en menos de dos minutos.

**No se entrena ningún modelo real en esta fase. No se descarga ningún dataset.**

El propósito de F0 es que a partir de aquí ningún error sea de infraestructura. Cuando en
F3 se rente una GPU, el código ya tiene que estar probado.

## Dependencias

Se declaran en `pyproject.toml` con grupos separados. La separación no es cosmética: es lo
que permite que la imagen de la API pese ~200 MB en lugar de ~2 GB.

| Grupo | Paquetes |
|---|---|
| `core` | numpy, pandas, pillow, pydantic, hydra-core, omegaconf |
| `train` | torch, torchvision, timm, lightning, albumentations, torchmetrics, scikit-learn, wandb |
| `api` | fastapi, uvicorn, onnxruntime, python-multipart — **prohibido torch, timm o lightning** |
| `dev` | pytest, pytest-cov, ruff, pre-commit |

**Ruedas de PyTorch.** En local se instalan las de CPU (`--index-url https://download.pytorch.org/whl/cpu`);
en la instancia de entrenamiento, las de CUDA. Documentar ambos comandos en el README y
dejar el flag en el Makefile. No fijar CUDA en el lockfile: rompería la instalación local.

El lockfile se versiona en git.

## Configuración con Hydra

`configs/config.yaml` compone los grupos `data`, `model` y `train`. Claves mínimas:

| Grupo | Claves |
|---|---|
| `data` | `root`, `manifest_path`, `splits_dir`, `image_size`, `batch_size`, `num_workers` |
| `model` | `backbone` (nombre timm), `pretrained`, `dropout`, `num_classes` |
| `train` | `seed`, `max_epochs`, `lr`, `weight_decay`, `precision`, `deterministic`, `accelerator` |

**Regla dura: cero constantes de configuración en el código.** Ningún tamaño de imagen,
tasa de aprendizaje ni ruta puede aparecer literal dentro de `src/`. Si aparece, es un bug.

Hydra guarda la config resuelta de cada corrida en su directorio de salida. Eso es lo que
después permite decir con precisión con qué parámetros se produjo cada número de la tesis.

## Fábrica de backbones — `src/melanoma/models/factory.py`

Contrato:

**Entrada:** nombre del backbone en timm, `pretrained` (bool), `num_classes`, `dropout`.

**Salida:** una tupla con
1. el módulo del modelo, y
2. un diccionario de configuración de datos obtenido de `timm.data.resolve_data_config`,
   con al menos `input_size`, `mean`, `std`, `interpolation`.

**Requisito crítico:** ese diccionario es la **única** fuente de la normalización en todo el
proyecto. Ninguna otra parte del código puede definir media, desviación ni escala de
píxeles. Esta es la barrera arquitectónica que impide repetir el error que produjo el
50.75 % de EfficientNetB3 en la versión anterior.

Cabeza del modelo, idéntica para todos los backbones: pooling global promedio → dropout →
capa lineal de una salida. Un solo lugar donde se define, no una por backbone.

---

## Semillas y determinismo — `src/melanoma/utils/seed.py`

Función única que fija Python, NumPy, PyTorch y los workers del DataLoader
(`seed_everything(seed, workers=True)`), y activa algoritmos deterministas cuando la
plataforma lo permite.

Documentar en el docstring, con honestidad: el determinismo completo cuesta velocidad, y
en GPU algunas operaciones siguen siendo no deterministas. Reportar reproducibilidad
perfecta bit a bit sería falso. Lo que sí se garantiza es que la misma semilla y la misma
config producen el mismo orden de datos y la misma inicialización.

## Prueba de humo — `scripts/smoke_train.py`

**Este es el entregable más importante de F0.**

- Datos: **sintéticos**, generados en memoria. 50 imágenes de ruido, etiquetas aleatorias.
  No descarga nada, no lee disco.
- Modelo: `resnet18` de timm con `pretrained=False`. No descarga pesos.
- 2 épocas, 224 px, CPU, batch 8.
- Lee su configuración de Hydra como cualquier corrida real.
- Debe terminar en **menos de 2 minutos** en la laptop.

**Por qué importa:** es el gate que se corre antes de encender cualquier instancia de GPU
pagada. Descubrir un `KeyError` a los 40 minutos de una corrida rentada es el modo de falla
que esta fase existe para cerrar. Corre también en CI.

## Pruebas — `tests/`

Cinco pruebas, todas rápidas, ninguna descarga nada:

| Prueba | Qué verifica |
|---|---|
| `test_config_loads` | La composición de Hydra carga y expone todas las claves declaradas |
| `test_seed_reproducible` | Dos llamadas con la misma semilla producen tensores idénticos |
| `test_factory_output_shape` | La fábrica devuelve salida de forma `(batch, 1)` para dos backbones distintos |
| `test_data_config_from_timm` | El diccionario de config trae `mean` y `std` reales del checkpoint, y **no** son valores triviales tipo `[0,0,0]`/`[1,1,1]` |
| `test_api_no_torch_import` | Ningún módulo bajo `services/api/` importa torch, timm ni lightning, ni directa ni transitivamente |

Las dos últimas son pruebas estructurales: codifican en el CI las dos decisiones de
arquitectura que más fácil se erosionan con el tiempo.

## Integración continua — `.github/workflows/ci.yml`

Disparadores: push y pull request sobre `main`.

Pasos, en orden, todos bloqueantes:

1. `ruff format --check`
2. `ruff check`
3. `pytest` con reporte de cobertura
4. `python scripts/smoke_train.py`
5. `docker build` de la imagen de la API
6. Verificación del tamaño de esa imagen: **falla si supera 400 MB**

El paso 6 no es capricho. Sin un límite automatizado, alguien —humano o modelo— agrega
torch a las dependencias de la API en tres meses y la separación entrenamiento/inferencia
se pierde en silencio.

## Makefile

| Comando | Efecto |
|---|---|
| `make setup` | Crea el entorno con uv e instala grupos core + train + dev (ruedas CPU) |
| `make setup-gpu` | Igual, con ruedas CUDA |
| `make lint` | ruff format + ruff check |
| `make test` | pytest |
| `make smoke` | Corre la prueba de humo |
| `make ci` | lint + test + smoke, lo mismo que corre GitHub Actions |

## Criterios de aceptación

Verificables uno por uno. La fase no se cierra si alguno falla.

1. `make ci` pasa en verde en la laptop.
2. El workflow de GitHub Actions pasa en verde en un push a `main`.
3. `make smoke` termina en menos de 2 minutos, medido con `time`.
4. `grep` de `src/` no encuentra ningún literal de tamaño de imagen, tasa de aprendizaje ni
   ruta de datos fuera de `configs/`.
5. La imagen Docker de la API construye y pesa menos de 400 MB.
6. Clonar el repositorio en un directorio limpio, correr `make setup` y `make ci`, y que
   funcione sin pasos manuales adicionales.
7. `uv.lock` está versionado en git.

El criterio 6 es el que realmente importa: es la definición operativa de "otra persona
puede correrlo", que es el primer punto de tu propia lista de críticas a la versión
anterior.

## Desviaciones respecto a la especificación

1. **`test_api_no_torch_import` → `test_api_dependency_isolation`.** Se renombró y se amplió
   para prohibir también el paquete `melanoma`, en las dos variantes (AST y subproceso).
   Motivo: importar `melanoma` reintroduce hydra y omegaconf en la imagen de la API.
2. **`src/melanoma/train/module.py`, no previsto en la spec.** Se agregó un LightningModule
   mínimo (`LitBinaryClassifier`). Motivo: la prueba de humo necesita un módulo que entrenar.
3. **`api` pasó de extra a grupo en `[dependency-groups]`.** Motivo: como extra heredaba
   `project.dependencies` y arrastraba pandas, hydra y omegaconf a la imagen de inferencia.
